# Task Tracker API

Асинхронный REST API сервис для совместного управления задачами и командами на базе FastAPI и PostgreSQL.

Проект спроектирован по принципам чистой архитектуры (Clean Architecture). Слой работы с данными реализован без использования ORM: взаимодействие с базой происходит через драйвер asyncpg с сырыми SQL-запросами, явным контролем транзакций и валидацией инвариантов на уровне схемы СУБД.

## Стек технологий

- Язык: Python 3.11+
- Веб-фреймворк: FastAPI
- СУБД: PostgreSQL
- Драйвер БД: asyncpg
- Очередь задач и брокер: Celery + Redis
- Безопасность: PyJWT, bcrypt, hashlib (SHA-256)
- Мониторинг: Prometheus client

## Архитектура и инженерные решения

### 1. Слой данных и целостность на уровне СУБД
- Работа с базой изолирована в слое репозиториев (Repository Pattern) через asyncpg. Это устраняет накладные расходы ORM на маппинг сущностей и исключает проблему N+1 запросов.
- Бизнес-правила защищены на уровне схемы базы данных:
  - Ограничение `chk_task_type` исключает возможность создания задачи, одновременно являющейся личной и привязанной к команде.
  - Написан PL/pgSQL-триггер `trg_team_members_count`, автоматически поддерживающий денормализованный счетчик участников команд при операциях INSERT/DELETE.

### 2. Конкурентность и версионирование задач (Optimistic Locking)
Для исключения состояния гонки (Race Condition) при одновременном редактировании задачи несколькими пользователями реализована оптимистическая блокировка. Каждое обновление сверяет переданное поле `version` с версией в БД и инкрементирует его. В случае конфликта сервер прерывает транзакцию и возвращает `409 Conflict`.

### 3. Аутентификация и управление сессиями
- Аутентификация разделена на Access-токены (JWT, 15 минут) и Refresh-токены (7 дней).
- Refresh-токены хранятся в защищенных `HttpOnly` cookie-файлах с флагом `SameSite=Lax`.
- В базе данных хранятся криптографические SHA-256 хеши токенов.
- Реализована ротация токенов: вызов эндпоинта `/auth/refresh` отзывает использованный токен и выпускает новую пару.
- Поддерживается как одиночный выход (`/auth/logout`), так и полный отзыв всех активных сессий пользователя со всех устройств (`/auth/logout-all`).

### 4. Ролевая модель (RBAC) и защита операций
- Участники команд разделены на роли: `admin`, `moderator`, `member`.
- Деструктивные действия (удаление команды владельцем или удаление аккаунта) требуют подтверждения текущим паролем (sudo-mode).

### 5. Фоновая аналитика (Celery + Redis)
Тяжелые агрегационные выборки вынесены из основного HTTP-процесса:
- Эндпоинт `POST /todos/analytics/compute` ставит задачу в очередь Celery, регистрируя запись со статусом `pending` в БД, и возвращает статус `202 Accepted` с идентификатором задачи (`job_id`).
- Воркер Celery рассчитывает метрики:
  - Среднее время выполнения завершенных задач в часах (`completed_at - created_at`);
  - Распределение по дням недели с учетом переданной клиентом таймзоны (валидация IANA timezones через модуль `zoneinfo`, при некорректной зоне возвращается `400 Bad Request`);
  - Топ-10 частотных слов в названиях задач с помощью регулярных выражений и `collections.Counter`.
- Эндпоинт `GET /todos/analytics` реализует паттерн опроса (polling): возвращает `202 Accepted`, пока расчет выполняется, и `200 OK` с готовым JSON после завершения.

### 6. Двухфазная загрузка вложений (Presigned URL Pattern)
Для предотвращения блокировки сетевого потока бэкенда большими файлами реализована двухэтапная схема:
1. Запрос ссылки на загрузку (`POST /todos/{id}/attachments/request-upload`): сервер проверяет права на задачу, проверяет размер файла (возврат `413 Payload Too Large` при превышении лимита) и MIME-тип (`415 Unsupported Media Type`), сохраняет метаданные и генерирует уникальный `storage_key`.
2. Бинарный поток файла отправляется клиентом методом `PUT /attachments/upload/{storage_key}` напрямую на целевой эндпоинт с валидацией размера в потоке.
3. При удалении (`DELETE /attachments/{id}`) происходит синхронное удаление файла из хранилища и удаление метаданных из БД.

### 7. Сквозной аудит и фоновая очистка
- Реализовано логирование 16 типов системных событий (создание/удаление задач и команд, авторизация, сброс сессий). Лог фиксирует IP-клиента, User-Agent, субъект и JSON-параметры изменений.
- Доступен эндпоинт `GET /admin/audit_logs` для администраторов с динамической фильтрацией по полям и пагинацией.
- В жизненном цикле приложения (Lifespan) работает асинхронный демон очистки, который раз в несколько минут удаляет отозванные токены и старые логи аудита.

### 8. Наблюдаемость (Observability)
- `GET /health` проводит проверку доступности PostgreSQL, Redis и прав на запись в файловое хранилище с замером сетевой задержки (latency в ms). При сбое компонента возвращается статус `503 Service Unavailable`.
- `GET /metrics` отдает данные в нативном формате Prometheus (счетчики общего числа запросов, ошибок и гистограмма времени ответа). Для предотвращения проблемы разрастания меток (High Cardinality) динамические URL нормализуются по шаблонам маршрутов (`/tasks/{id}`).

## Структура проекта

```text
app/
├── api/
│   ├── deps.py             # Зависимости FastAPI (проверка прав, JWT, RBAC)
│   ├── monitoring.py       # Эндпоинты /health и /metrics
│   └── v1/
│       ├── admin.py        # Журнал аудита для администраторов
│       ├── analytics.py    # Эндпоинты аналитики
│       ├── attachments.py  # Загрузка и удаление файлов
│       ├── auth.py         # Аутентификация, ротация сессий
│       ├── tasks.py        # Управление задачами, версионирование
│       ├── teams.py        # Команды и управление участниками
│       └── users.py        # Профиль пользователя
├── background/
│   ├── analytics_worker.py # Фоновые задачи Celery
│   └── cleanup.py          # Фоновый демон очистки в Event Loop
├── core/
│   ├── celery_app.py       # Конфигурация Celery
│   ├── config.py           # Настройки (Pydantic Settings)
│   ├── database.py         # Пул соединений asyncpg
│   ├── metrics.py          # Prometheus middleware
│   └── security.py         # Хеширование паролей и генерация токенов
├── repositories/           # Слой доступа к данным (Raw SQL)
├── schemas/                # Схемы валидации данных (Pydantic)
scripts/
├── init.sql                # DDL-схема базы данных, индексы, триггеры
└── init_db.py              # Скрипт инициализации таблиц через asyncpg
uploads/                    # Локальное хранилище файлов
main.py                     # Точка входа, lifespan, регистрация middleware
```

## Установка и запуск

### 1. Клонирование репозитория и окружение
```bash
git clone https://github.com/Hayamus/Task-Tracker-API
cd <папка-проекта>

python -m venv venv
```

Активация окружения:
- Windows (PowerShell):
  ```powershell
  .\venv\Scripts\Activate.ps1
  ```
- Linux / macOS:
  ```bash
  source venv/bin/activate
  ```

Установка зависимостей:
```bash
pip install -r requirements.txt
```

### 2. Настройка конфигурации (.env)
Создайте файл `.env` в корневой папке проекта:
```ini
ENVIRONMENT=develop
SECRET_KEY=change-this-to-a-secure-secret-key-min-32-chars
ACCESS_TOKEN_EXPIRE_MINUTES=15
REFRESH_TOKEN_EXPIRE_DAYS=7

DATABASE_URL=postgresql://postgres:postgres@localhost:5432/task_tracker
REDIS_URL=redis://localhost:6379/0

MAX_FILE_SIZE_BYTES=10485760
UPLOAD_DIR=uploads
```

### 3. Запуск сервисов инфраструктуры
Если PostgreSQL и Redis не запущены локально, их можно поднять в Docker:
```bash
# Redis
docker run -d --name redis-broker -p 6379:6379 redis:alpine

# PostgreSQL
docker run -d --name postgres-db -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=task_tracker -p 5432:5432 postgres:16-alpine
```

### 4. Инициализация схемы базы данных
Для создания всех необходимых таблиц, ограничений целостности, индексов и триггеров выполните команду:
```bash
python -m scripts.init_db
```

### 5. Запуск воркера и веб-сервера

В первом терминале запустите воркер Celery:
- Linux / macOS:
  ```bash
  celery -A app.core.celery_app.celery_app worker --loglevel=info
  ```
- Windows:
  ```powershell
  python -m celery -A app.core.celery_app.celery_app worker --loglevel=info --pool=solo
  ```

Во втором терминале запустите веб-сервер FastAPI:
```bash
python -m uvicorn main:app --reload
```
